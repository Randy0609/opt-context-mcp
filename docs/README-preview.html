OPT Context MCP

一个人的 AI 团队，从一份可用的业务上下文开始。

OPT Context MCP 是面向中小企业老板和创业者的开源项目计划：把你选定的业务资料，通过统一接口提供给获准的 AI，让它们做任务前能查找相关原文，回答时说明出处、版本和缺口。

理解这个项目，可以从名字里的三部分开始：OPT、Context、MCP。

项目状态：首版规划中。
本仓库当前提供项目介绍与实施路线。可分发程序、正式安装命令、客户端支持矩阵和开源许可证尚未提供；完成验收后再更新发布状态。

1. OPT 是什么：一个人的 AI 团队

OPT = One Person Team，中文在本项目中称为“一个人的 AI 团队”。

一个人负责目标、判断和结果，把适合的任务交给 AI，并通过工作流组织执行。

在这个团队里，可以有负责内容的 AI、负责项目的 AI、负责资料检索的 AI。它们可以是不同工具、不同 Agent，也可以是同一工具中承担不同职责的助手。具体能做什么，需要按任务验证。

团队中的角色负责什么
你设定目标、提供依据、作出决定、对结果负责
AI 助手根据任务与获准资料，起草、查找、分析和执行支持的操作
工作流明确输入、步骤、交付标准和需要人工确认的环节

这个项目关注其中一个基础问题：这支 AI 团队从哪里了解你的业务？

2. 为什么是 Context：让 AI 有做事的业务背景

Context 就是上下文。在这里，它指完成具体任务所需要的业务背景、依据和约束。

例如：

  • 你是谁，公司做什么，服务哪类客户。
  • 产品如何定义，哪些承诺已经确认。
  • 当前项目要达到什么目标，推进到哪一步。
  • 过去作过什么决定，依据是什么，是否仍然适用。
  • 工作流程有哪些步骤，交付标准是什么。
  • 当前任务面向谁，可以使用和提供哪些资料。

同样是“写一份产品介绍”，面向新客户还是渠道伙伴、采用哪版产品定义、允许承诺什么，都会影响内容。这个例子说明了本项目想解决的问题：让 AI 先取得相关背景，再处理任务。

你可能已经遇到这样的情况：

  • 开一个新对话，又要介绍一遍公司、产品和客户。
  • 换一个 AI 助手，又要重新复制背景资料。
  • AI 写出了流畅的内容，却沿用旧产品介绍或过期政策。
  • 给顾问或合作伙伴布置任务时，资料散在几个文档和聊天里。

OPT Context MCP 希望让这些资料在你选定的位置维护，由获准的 AI 按任务查找和读取。资料应带有来源、版本与核对时间；没有确认的内容要保留缺口。

你可以把业务上下文看作团队的工作依据。AI 需要哪一部分，就取用哪一部分；原文仍是判断和引用的起点。

这个项目的目标是减少反复补充背景的负担。能减少多少、是否改善业务交付，需要通过实际试用验证。

3. 为什么做 MCP：给 AI 一个统一的取用接口

MCP = Model Context Protocol，模型上下文协议。 它让 AI 应用连接本地或远程服务，调用服务提供的工具和上下文。MCP 官方文档

在 OPT Context MCP 中，我们计划用这个接口处理三件事：

  1. 查什么：根据任务找到相关资料，再读取必要的原文。
  2. 谁能查：不同客户端用自己的身份，只读取获准范围。
  3. 查到了什么：返回出处、版本、核对时间、截断范围和已知缺口。

采用 MCP 的设计理由是，让经过验证的客户端复用这套资料取用方式。多个 AI 可以从同一批来源取得材料，而来源仍由你管理。

三个词在本项目中的关系是：

OPT 说明谁来做事；Context 提供做事的背景与依据；MCP 提供取得这些资料的接口。

OpenAI 的支持，以及 GitHub 与托管的关系

OpenAI 官方文档已经说明：Codex 支持本地 stdio 和远程 Streamable HTTP MCP 服务；ChatGPT 网页端可以通过插件使用远程 MCP 工具。不同产品入口的接入方式与权限需要分别确认。OpenAI MCP 接入说明

OpenAI 的 Sites 提供托管和分享能力，访问选项取决于账号、工作区设置及功能开放情况。OpenAI Sites 文档

这为本项目提供了本机和在线两种实现方向。我们计划先通过 GitHub 提供可审阅的代码、资料组织方式、模板与安装说明，随后验证适合的托管方式。

读取结果：出处 · 版本 · 核对时间 · 缺口

计划中的一次使用过程：

  1. 检查当前身份获准读取的资料范围。
  2. 根据任务找到相关候选资料。
  3. 读取必要的原文片段。
  4. 带着引用回答；资料缺失、过时或无法读取时，明确说明。

找到资料不代表已经读懂，提供给模型也不代表模型一定正确使用。客户端的实际取材和回答仍需要验收。

检索、权限与引用核心应独立于部署方式。增加托管版时，另行适配在线运行环境、身份认证和来源连接；本机的文件路径与账号配置不能直接视为云端可用。

让多个 AI 使用同一份上下文

项目计划让不同的获准客户端读取同一批来源，避免分别维护多份背景材料。

每个客户端应有自己的读取身份和范围。例如，内容助手读取产品与表达规范，项目助手读取项目与流程资料。增加一个客户端，需要单独配置并验证它实际读取到了什么。

“多个客户端共用来源”是产品目标；各客户端是否支持、是否会主动调用，以及调用后能否正确使用，以实际验收记录为准。

给上下游使用

软件分发与资料共享需要分别处理：

  • 朋友安装软件：使用同一套程序，接入他自己的业务资料。
  • 你提供合作资料：由你选出适合特定接收方的内容，再提供给对方。

合作资料包是后续计划。举例来说，供应商需要产品规格和交付要求，渠道伙伴需要产品介绍和渠道规则，顾问需要相关项目目标与进度。

合作包应经过内容预览，并标明版本、日期和适用对象。离线资料包一旦发出，源文件更新不会自动更新对方副本，撤销源权限也无法销毁已经取得的副本。

需要跨公司持续读取最新资料时，将另行设计托管运行、在线共享及授权，并测试接收方的实际客户端。首版的本机服务不具备这个交付承诺。

数据与权限边界

  • GitHub 仓库用于提供程序、文档、空模板和明确标注的虚构示例。真实业务资料和凭证由使用者自行保管。
  • 核心以只读来源为设计原则；任何本地元数据记录或可选记忆整理都应单独说明。
  • 资料放在本机，不等于读取片段永不离开电脑。AI 客户端可能把片段放进其云模型对话，需要同时考虑该客户端的数据处理方式。
  • MCP 的权限约束其读取接口。同一系统账户下拥有文件或 shell 权限的 Agent，可能直接访问原文；这不能替代操作系统或企业级隔离。
  • 来源正文是任务材料。正文里的指令不能覆盖用户指令或扩大授权范围。
  • 资料日期、检索命中和模型总结，都不能单独证明业务事实真实、最新或完整。

如何开始

目前可以先选择一个真实、重复、答案可核对的任务，准备相关资料。

正式安装说明将随首个经过验收的版本提供。发布后，交付目标是：阅读安装说明 → 检查运行条件 → 选择资料目录 → 完成示例验证 → 验证本人选定的一条原文 → 学会撤销和卸载。

在正式安装说明发布前，不提供未经验证的一键命令，也不要求用户复制个人环境中的配置。
